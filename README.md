# token-panel · WorkBuddy Token 实时用量面板

一个常驻在本机的只读小面板，实时显示 WorkBuddy 烧掉多少 token。
纯 Python 标准库，不装依赖、不联网、不写任何 WorkBuddy 的数据。

## 怎么用

| 想做的事 | 操作 |
|---|---|
| **桌面双击打开** | 双击桌面上的 `Token 面板.cmd`（等同于下一行） |
| 打开面板 | 双击 `start-panel.bat`（会在后台起来并自动开浏览器） |
| 关掉面板 | 双击 `stop-panel.bat` |
| 开机自动起 | 双击 `install-autostart.bat`；撤销用 `uninstall-autostart.bat` |
| 只想看一眼数字 | `python server.py --once` |
| 换端口 | `python server.py --port 8780 --open` |
| 报错时自检 | `python tools/selftest.py` |
| 看性能 | `python tools/bench.py` |

面板默认在 <http://127.0.0.1:8770/>，只监听本机回环地址，局域网里别的机器访问不到。

打开后浏览器收藏这个地址，就是一个常驻入口。整页数据都会自己跟着变：有新事件时最多 1.5 秒内更新一次，没变化时页面完全静止（不重绘、不闪烁）。

## 移植到别的电脑

```bat
python tools\pack.py
```

生成 `dist/token-panel-<版本>.zip`，约 0.4 MB。包里**不含 `data/`**（那是本机的索引与日志）。
拷过去解压，装上 WorkBuddy（或 Python 3.7+），双击 `start-panel.bat` 即可；
首次会全量扫一遍历史，之后都是增量。

**零第三方依赖**：后端只用标准库，前端 ECharts 已本地打包，不需要 npm、不需要 `pip install`、
不需要数据库服务。平台相关代码只集中在 `tools/launch.py` 和几个 `.bat`，
`server.py` 等核心模块不含任何平台判断。

升级时**只替换代码文件，保留 `data/`**。详见 `docs/移植与升级.md`。

> 注意：面板读的是**本机**的 `~/.workbuddy`，两台电脑各算各的，不会自动合并。

三种组合的行为：

| 当前状态 | 按 S | 按其他键 |
|---|---|---|
| 未运行 | —— | 启动面板，关窗口，面板继续跑 |
| 已在运行 | 停止面板（数据与索引保留） | 只关窗口，面板继续跑 |

按键用 `msvcrt.getwch()` 读取，**单键立即生效，不需要回车**。

配色约定：logo 青色、步骤序号灰色、`√` 绿色、`!` 黄色、`×` 红色、结尾方框绿色。
方框里刻意不放 `√` 这类"歧义宽度"字符——控制台按双宽渲染会让边框错位。

实现分三层，各管一件事：

| 文件 | 职责 | 编码 |
|---|---|---|
| `Token 面板.cmd`（桌面） | 找到项目目录，**在同一个窗口**接着跑 | 纯 ASCII |
| `start-panel.bat` | 定位解释器（跳过商店占位符），调用启动器 | 纯 ASCII |
| `tools/launch.py` | 画 logo、分阶段检查、拉起服务、等待按键 | UTF-8 |

`start-panel.bat` 里**没有 `start` 命令**——正是它之前另开一个控制台，导致第一个窗口闪一下就没了。

## 屏幕上是什么

- **时间选择** —— 顶栏可选：今天 / 昨天 / 前天 / 近 7 天 / 近 30 天。切换后，KPI、按小时、占比、项目 TOP5、会话 TOP5 一起跟着变。趋势图另有独立的 30/90 天开关（趋势需要长周期才看得出形状）。
- **账号** —— 顶栏常驻当前账号名（默认"账号 xxxxxxxx"，xxxx 是 WorkBuddy 账号 UUID 前 8 位），旁边是账号筛选：全部 / 各账号 / 未归属。
  每个账号的名字都互不相同；想换成好记的昵称，在 `config.py` 的 `ACCOUNT_ALIASES` 里按前 8 位填写即可。
  选中某个账号后，整页（KPI、占比、TOP5、趋势、热力图）都只看这个账号；饼图切到"账号"档就是按账号拆分。
  点右侧 `⇄` 看**切换时间线**：什么时候从哪个账号换到了哪个账号。详见下面「账号是怎么区分的」。
- **会话卡（随区间换主角）** —— 选"今天"时主角是**当前正在跑的那条会话**，大数是今日消耗；
  选历史区间时主角变成**该区间里最贵的那条会话**，大数是它在区间内的消耗。
  标题后面固定挂会话名，副标题第一行是"区间/今日积分 · 有多少轮真拿到了积分记录"，
  第二行灰字是**模型名 + 这条会话的历史累计**（次要）。
  右上角是**状态灯**：绿=正在消耗/活跃（距最后一条事件 < 90 秒）、黄=空闲 N 分（< 1 小时）、
  灰=已结束 · X 前（≥ 1 小时）；切到历史区间时固定显示灰色"历史会话"。
  判定依据是心跳文件 `~/.workbuddy/sessions/*.json` 的 `lastHeartbeat` 与最后一条事件的时间戳。
- **区间累计** —— 所选区间的 token 合计 + 积分合计，并标出"多少轮有积分记录"、日期范围与轮数。
- **轮均消耗 / 区间日均** —— 单日区间看轮均（一天算"日均"等于累计，没信息量），多日区间看日均；
  积分分母只算**有积分记录的那几轮/那几天**（没记录的轮是"不知道"，不是 0 分）。
- **缓存命中率** —— 跟随所选区间，副标题里附**全历史积分**与真实覆盖率（覆盖 = 有积分记录的请求数 / 全部请求数）。
- **按小时** —— 单日看该日 24 小时；多日区间是"各小时合计"，用来找习惯性高峰。
- **积分** —— 来自 `workbuddy.db` 的 `session_usage`，靠 `conversationRequestId` 对回转录。
  **没记录的显示 `—`，不显示 `0.00`** —— 免费模型是真 0 分，没记录是不知道，两者不能长一个样。
  token 与积分仍是两个独立口径，不要互相换算。
- **今日按小时** —— 24 根柱子，当前小时高亮，虚线是昨天。
- **模型 / 项目占比** —— 今日的量按模型或按工作区拆开。
- **项目消耗 TOP 5** —— 今日花在哪几个工作区，横向条形看绝对量差距。
  项目名优先取 WorkBuddy 里的「项目空间显示名」（`~/.workbuddy/workspace-display-names.json`），没改过才回退目录名；
  在 WorkBuddy 中重命名空间后，看板会自动跟着变，无需重启。
- **会话消耗 TOP 5** —— 最贵的几次对话，第一名高亮；每行「序号 + 会话名 + 模型名」，
  条形右侧是「token · 积分」，悬停可看完整会话名、模型、轮数、时长、积分覆盖与历史累计。
  这一块用行布局而不是图表：卡片高时一行占两行（名称 / 模型占一行、条形在下一行），
  卡片矮到放不下时自动切成单行（名称 名称 模型 条形 数值），任何高度都不会出现文字互压。
- **每日趋势** —— 近 30 / 90 天，附 7 日移动平均。
- **52 周热力图** —— 颜色越深，那天烧得越多。

趋势和热力图并排各占一半宽度（面积减半、高度保留），是为了给上面两块 TOP 5 腾地方——
把两张图的高度各压一半会把坐标轴和热力图标签压烂，反而更难读。

右上角 `◐` 切换明暗主题；`?theme=dark` 可以直接用暗色打开。

## 数字是怎么算的（重要，防止以后自己怀疑）

1. **token 口径**：优先取 `providerData.usage`，缺失才退回 `message.usage`，同一条记录**只算一次**。`totalTokens` 为 0 时用 input+output 回填。
2. **轮数**：`COUNT(DISTINCT conversationRequestId)`。一次用户提问可能触发几十次模型调用，那些都算**一轮**——所以"1 轮"配几百万 token 是正常的。
3. **累计值看着吓人**：缓存命中率常年在 98% 以上，4 亿 token 里约 3.9 亿是缓存读取，实际增量很小。所以这里把缓存命中率单独做成一张卡，别被总数误导。
4. **credit 是另一套口径**：来自 `~/.workbuddy/workbuddy.db` 的 `session_usage` 表，靠 `conversationRequestId` 对回转录。
   覆盖率 = **有积分记录的请求数 / 全部请求数**（实测约 48%，且随时间波动），界面上一直标着它。
   另有一批会话根本不在 `session_usage` 里（被清理的老会话、自动化工作区等），这些轮次永久没有积分数据 ——
   所以积分只反映"记到账的部分"，别拿它和 token 折算。读取失败时显示"不可用"，**不影响 token 统计**。
5. `session_usage.used / size` 是**上下文窗口占用**，不是 token 消耗，这里只不用它算总量。
6. 切日切时按本机时区（UTC+8），并且在建索引时就写进库，查询阶段不再换算。

## 数据从哪来

| 来源 | 路径 | 用途 | 必需 |
|---|---|---|---|
| 会话转录 | `%USERPROFILE%\.workbuddy\projects\**\*.jsonl` | 所有 token 数字 | 是 |
| 会话心跳 | `%USERPROFILE%\.workbuddy\sessions\*.json` | 识别"当前会话" | 否 |
| 本地库 | `%USERPROFILE%\.workbuddy\workbuddy.db` | credit + **账号归属**（只读） | 否 |

只读，绝不修改上面任何文件。索引库在 `data/index.db`，删掉会自动重建。

## 账号是怎么区分的

转录文件里**没有账号字段**，所以归属只能事后补：`workbuddy.db` 的 `sessions` 表有一列 `user_id`，
采集线程每 30 秒把它读进索引库的 `accounts` 表（会话 id → 账号），查询时用 `session_id` 关联。
因此：

- **换账号不会改变任何路径**，`~/.workbuddy` 始终是同一个目录，新旧数据天然混在一起；能区分开全靠这张映射表。
- 映射延迟最多 30～60 秒。刚切号、刚开的新会话，这一小段时间的用量会先显示成**未归属**，随后自动归位。
- 转录里存在、但 `workbuddy.db` 里已经没有记录的会话（被清理掉的旧会话、子代理会话），会一直留在**未归属**。
  这不是算错，`/api/status` 的 `audit` 会给出 `sessions_unknown` 与未归属占比，用于核对。
- 账号默认显示带 UUID 前 8 位的名字（如 `账号 1a2b3c4d`），**不会多个账号共用同一个名字**；不读邮箱、不读昵称，也不联网。悬停账号名可以看到完整 UUID。
  想自定义：在 `config.py` 的 `ACCOUNT_ALIASES` 里按完整 UUID 或前 8 位填昵称，名字模板由 `ACCOUNT_NAME_TEMPLATE` 控制；
  万一两个账号填了同一个昵称，后端会自动补 UUID 短码区分。
- 切号记录存在 `data/index.db` 的 `account_switches` 表，保留 180 天。
- 一致性自检：`各账号之和 + 未归属 == 全站总量`（`audit.balanced`），任何一次 SQL 写错都会在这里暴露。

## 为什么能"实时"

冷启动把转录全量扫一遍，约 1～2 秒；之后每条转录都记着"读到第几个字节"，
每秒钟只看新增的那一段。

四种边界都做了处理，测试见 `tools/selftest.py`：

- 最后一行还没写完 → 不消费，下一秒再读
- 文件被截断或重写 → 清空该文件的事件重读，防止重复计数
- 同名文件被替换（inode 变）→ 同上
- 单行超过 8 MB → 整段跳过并记日志

### 整页实时是怎么做的

**数据变了才推、变了才画**，不是每 1.5 秒无脑重算一遍。

```
索引器写入 ──bump()──► Store.seq ──变了才发──► SSE 推 {"v":123……}（62 字节）
                            │                        │
                            └─► 聚合缓存按 v 失效      └─► 前端收到 v 变了
                                                          └─► GET /api/bundle 一次拿全
```

三条原则：

1. **SSE 只负责"新鲜度"，数据走 HTTP**。趋势的天数（30/90）、热力图的周数（26/52）
   是浏览器自己的参数，服务端预知不了 —— 广播完整快照必然会漏掉那几张图。
   所以推一个版本号，页面按自己的参数去 `/api/bundle` 取一次全量。
2. **变了才推**。`seq` 是单调递增的数据版本号，写在 `Store` 里，由任何"会改变统计结果"
   的写库动作触发（新增事件、截断重写、credit 更新、跨日、会话切换）。
   数据没变时只每 10 秒发一个心跳，用来让丢帧的客户端自愈。
3. **变了才画**。每个渲染函数入口先比一次数据指纹，没变就整块跳过。
   三张图原来是 `notMerge: true`（每轮重建组件、入场动画重播），现在改成 `merge` +
   固定 series id，悬停中的 tooltip 不会被打断。

代价（实测，单核百分比）：

| 状态 | 聚合 SQL | 索引器 | 网络/客户端 |
|---|---|---|---|
| 改造前 | 32ms / 1.5s ≈ 2.2% | 71ms / 1s ≈ 7.1% | 3.65 KB/s |
| 现在（空闲） | **0** | **5ms / 拍 ≈ 0.5%** | **12 B/s** |
| 现在（活跃） | 48–125ms / 次，1.5 秒合并 | 同上 | ~8 KB/s |

### 没人在看的时候会自己"打盹"

打开面板时每秒扫一次；**浏览器一关，间隔自动放宽到 5 秒**。
标签页切到后台超过 60 秒会主动断开连接，切回来时重连并补一次全量。
再次打开会立刻醒过来（有连接时立即恢复 1 秒，最坏延迟不到 1 拍）。

`discover()` 原来每拍都完整 `os.walk` 一遍：153 个目录、2263 个目录项，实测 36ms。
现在按目录 mtime 增量枚举（增删文件一定会改变所在目录的 mtime，所以新文件照样立刻发现），
每 30 拍仍强制全量重扫一次兜底 —— 36ms 降到 **2.4ms**。

想看它现在是什么状态，不用开浏览器：

```bash
curl -s http://127.0.0.1:8770/healthz
# clients / scan_interval / seq / cache 都在里面
# clients=0, scan_interval=5.0  -> 待机中
# clients=1, scan_interval=1.0  -> 有人在看
# 静默时 seq 不变、cache.miss 不涨，说明"变了才推"真的生效
```

credit 也只在 `workbuddy.db` 真的变了才重算（用一条聚合指纹判断，约 1 毫秒），
没变化时直接跳过，省掉 400 次点查和 400 行写库。

## 目录里都是什么

```

├─ config.py            路径、端口、扫描预算集中在这里
```

## 出问题了

| 现象 | 原因与处理 |
|---|---|
| **双击没反应 / 黑窗一闪就没** | 多半是 `python` 被解析成了应用商店的 0 字节占位符。`start-panel.bat` 已内置查找逻辑（优先 WorkBuddy 自带解释器），若仍失败看 `%TEMP%\tp-launch.log` 里记录的 `interpreter=` 与 `errorlevel=` |
| **`python --version` 没有任何输出** | 同上：那是商店占位符，不是真解释器。用完整路径验证：`& "$env:USERPROFILE\.workbuddy\binaries\python\versions\3.13.12\python.exe" --version` |
| 打开是空白页 | 先看 `data/panel.log`；再用上面的完整路径跑 `server.py --once` 看能不能读到数据 |
| 端口被占 | 会自动往后找 8770–8779；也可以 `--port` 指定 |
| 数字不涨 | 确认 WorkBuddy 正在对话；点一下页面刷新看 SSE 是否连上（右上角应显示"实时"） |
| credit 显示不可用 | `workbuddy.db` 正被占用或拒绝访问，属正常降级，token 不受影响 |
| 想清空重来 | 删掉 `data/index.db*`，重启面板即可，只会慢一次 |
