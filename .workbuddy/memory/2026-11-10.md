## 架构审查（元筑/系统架构师视角，仅分析，未改动任何项目代码）

用户目标：可移植性高（可给别人用）、使用方便、内存占用小、环境依赖小。

结论：架构主体不需要重构。纯标准库 + 单文件 SQLite(WAL) + seq 版本驱动缓存 + SSE 只推版本号 + 索引器降频，已基本满足「环境依赖小 / 内存小」；短板集中在 Windows 启动层、配置外置与安全边界一致性。

实测（不改数据）：
- 服务当前未运行（127.0.0.1:8770/healthz 无响应）
- data/index.db 13.9 MB / events 18,683 / credits 455 / files 93 / accounts 85 / 20 天数据
- 标准库全导入进程工作集 27.4 MB；打开 14 MB 索引库 + 跑聚合 SQL 后 37.1 MB（稳态服务估计 40–60 MB）
- Python zipfile 对中文文件名自动写 UTF-8 标志位 0x800（当前 pack.py 无编码 bug，旧解压工具仍可能乱码）

关键问题清单：
1. config.HOST=0.0.0.0 且 server._host_ok() 允许 RFC1918 私有网段，与 README「只监听本机回环」矛盾；docs/device-token-patch.md 的访问令牌 + cloudflared 隧道补丁**未落地**（server.py 无 hmac/ACCESS_TOKEN/--token）。仅校验 Host 头、无来源 IP 校验与鉴权。
2. 启动层 Windows 专属：5 个 .bat；tools/launch.py 用 ctypes/msvcrt/taskkill/chcp/pythonw 并写死 python.exe 探测；tools/autostart.py 用启动文件夹 + mbcs。核心 5 个 py 模块无平台判断。
3. launch.py 只 healthz(DEFAULT_PORT)，而 server.pick_port 会顺延 8770–8779；端口被占时启动器会误报「服务 20 秒未响应」，实际服务已在其他端口运行。
4. ACCOUNT_ALIASES / 端口 / 数据源路径写死在 config.py，用户改源码，升级覆盖即丢。
5. aggregate.Aggregator._memo 从不淘汰；acct 已白名单化，但 days(7–365)/weeks(4–104) 仅钳制范围未离散化，可缓存大量完整快照 —— 唯一的内存放大面。
6. web/index.html(77 处) 与 web/index.readme.html(60 处) 被注入 data-page-node-id / pnid 注释，并引用 /page/page_comm/inject.js，发行包需清理。
7. notify.py 会向企业微信发 HTTPS 出站，与 README「不联网」表述冲突（应标注为可选）。
8. README/HANDOFF 称「两台电脑路径必须完全一致」属过度约束：config.ROOT 用 __file__、bat 用 %~dp0，代码无硬编码绝对路径。

建议分级：
- P0：默认绑 127.0.0.1，局域网访问改显式 --host/--token 并补来源 IP 校验 + 同步文档；修启动器端口顺延探测；清注入残留与文档表述。
- P1：跨平台 panel.py start|stop|status|once（.bat 降为快捷方式）；配置外置 data/settings.json + --workbuddy-dir；_memo 加 LRU 上限与参数白名单。
- P2：前端按需引入 ECharts（降浏览器内存）、索引库可选保留期。不建议 PyInstaller 打包：体积/内存反增，与用户目标冲突。

验收指标：另一台 Windows 与一台 macOS/Linux 能一键起页；/healthz 可读 clients/seq/cache；稳态 RSS < 60 MB；解压无乱码；升级后自定义昵称保留。
